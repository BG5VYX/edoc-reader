# 证件识读（eDoc Reader）

一个**完全离线、无需任何授权文件**的 Android 电子证件读取应用：
先用摄像头 OCR 识别证件机读区（MRZ），再通过 NFC 读取护照 / 往来港澳通行证 / 往来台湾通行证
的芯片数据，按 ICAO Doc 9303 解析并做被动认证，结果保存在本机并支持批量导出。

> 本项目的起点是对国家移民管理局《出入境证件电子信息识读认证 SDK》（Android / Windows 版）
> 的逆向分析。完整的原理与方案说明见
> [`docs/出入境证件识读技术报告.pdf`](docs/出入境证件识读技术报告.pdf)（26 页，含协议握手时序图），
> Markdown 版分析见 [`docs/SDK-分析报告.md`](docs/SDK-分析报告.md)。

---

## 它和官方 SDK 的关系

官方 SDK 的读证能力依赖**授权文件 + 设备指纹 + 服务端校验**，没有授权文件无法工作。
但读证流程本身完全由公开国际标准（ICAO Doc 9303）定义，因此本项目**从零实现**了同一套流程：

| 环节 | 官方 SDK | 本项目 |
|---|---|---|
| MRZ 识别 | Tesseract + 护照专用训练集 / 自研 OCR 引擎 | Google ML Kit 文本识别（模型随 APK 打包，**离线**）+ 自研 MRZ 行组提取与校验位纠错 |
| 芯片通道 | 手机 NFC / PC-SC | Android `IsoDep` + NFC Reader Mode |
| 认证 | BAC（原生实现） | **自研 BAC**，已用 ICAO 9303-11 附录 D 官方向量逐字节验证 |
| 传输 | 3DES 安全报文 | **自研安全报文**（DO'87'/'85'/'97'/'99'/'8E'） |
| 解析 | 原生实现 | **自研** BER-TLV / DG1 / DG2 / DG11 / DG14 / DG15 解析 |
| 验证 | OpenSSL + CSCA 库 + 服务端 | **自研** DER/CMS 解析 + Android JCE 验签 |
| 信任链 | 内置中国 CSCA 库 | **内置 513 张 CSCA 证书，覆盖 103 个国家/地区**（德国 BSI + 荷兰 NPKD 公开主列表） |
| 主动认证 | 支持 | **自研**，用 DG15 公钥验证芯片签名，可排除芯片克隆 |
| 联网 | 必须 | **完全不需要** |
| 授权文件 | 必须 | **不需要** |

代价：无法给出官方 SDK 那种"服务端查验结论"（例如实时吊销状态、服务端黑名单比对）。
但完整信任链判定**已经实现**：内置 CSCA 主列表，可独立给出「签发国可信」的结论。

## 功能

- **OCR 识别 MRZ**：CameraX 实时预览 + ML Kit Latin 文本识别，自动提取 TD1 / TD2 / TD3 行组，
  计算并校验各校验位（含复合校验位），对 OCR 常见的字母/数字混淆做**有限度自动纠错**；
  识别失败时可手动输入。
- **NFC 读取芯片**：BAC 双向认证 → 3DES 安全报文 → 依次读取 EF.COM、DG1、DG2、DG11、DG14、
  DG15、EF.SOD。
- **被动认证**：本地重算各数据组摘要并与 EF.SOD 中的 LDS Security Object 比对；解析 CMS
  SignedData 并用内嵌的文档签名证书（DSC）验证签名。
- **CSCA 信任链验证**：内置 513 张 CSCA 公钥证书（覆盖 103 个国家/地区，含中国护照、
  中国香港、中国澳门及中国台湾地区），把文档签名证书沿签发关系逐级上溯到签发国根证书，
  给出「签发国可信」的完整结论。
- **主动认证（AA）**：向芯片发送随机挑战值，用 DG15 中的公钥验证芯片签名——
  这是唯一能排除**芯片克隆**的机制。被动认证与 CSCA 信任链都无法识破克隆芯片
  （攻击者可原样复制全部数据使摘要与签名自洽），只有 AA 能。
- **本地保存**：结构化记录 + 芯片人脸图像，存于应用私有目录（卸载即清除，且已排除系统备份）。
- **批量导出**：JSON / CSV / ZIP（含人脸图像），通过系统文件选择器保存，无需存储权限。

## 编译

环境要求：JDK 17+、Android SDK（compileSdk 34、build-tools 34.0.0）。

```bash
# 1) 指定 SDK 路径
echo 'sdk.dir=/path/to/Android/sdk' > local.properties

# 2) 编译
./gradlew assembleDebug     # 产物：app/build/outputs/apk/debug/app-debug.apk
./gradlew assembleRelease   # 产物：app/build/outputs/apk/release/app-release.apk
```

也可以直接用 Android Studio 打开工程目录。

## 使用

1. 安装 APK，打开应用。
2. 点右下角「读取新证件」。
3. 把证件资料页下方的 MRZ 放进取景框（护照 2 行、通行证卡 3 行），等待识别成功。
   - 识别不出来可以点「手动输入 MRZ」。
4. 自动进入读卡页，把手机 NFC 感应区贴住证件芯片位置，保持不动直到提示"读取成功"。
5. 在详情页查看证件信息、人脸图像、DG11 附加资料、被动认证结果与原始 MRZ。
6. 首页右上角「批量导出」可选择 JSON / CSV / ZIP。

## 算法正确性

BAC 与安全报文的实现已用 **ICAO Doc 9303-11 附录 D 的官方工作样例**逐字节验证：

| 中间量 | 官方值 | 本项目 |
|---|---|---|
| `Kseed` | `239AB9CB282DAF66231DC5A4DF6BFBAE` | ✅ 一致 |
| `Kenc` | `AB94FDECF2674FDFB9B391F85D7F76F2` | ✅ 一致 |
| `Kmac` | `7962D9ECE03D1ACD4C76089DCE131543` | ✅ 一致 |
| `E.IFD` | `72C29C2371CC9BDB65B779B8E8D37B29ECC154AA56A8799FAE2F498F76ED92F2` | ✅ 一致 |
| `M.IFD` | `5F1448EEA8AD90A7` | ✅ 一致 |
| `K.ICC` | `0B4F80323EB3191CB04970CB4052790B` | ✅ 一致 |
| `KsEnc'` | `979EC13B1CBFE9DCD01AB0FED307EAE5` | ✅ 一致 |
| `KsMac'` | `F1CB1F1FB5ADF208806B89DC579DC1F8` | ✅ 一致 |
| `SSC` | `887022120C06C226` | ✅ 一致 |

输入为 `MRZ_information = L898902C<369080619406236`。

上述断言全部固化在单元测试中，共 **99 个用例全部通过**：

```bash
./gradlew testDebugUnitTest
# DesCryptoTest        9 个用例 —— KDF / Retail MAC / 填充 / E.IFD / M.IFD / 会话密钥 / SSC
# MrzParserTest       19 个用例 —— 校验位 / TD3 / TD1 / 行组提取 / 纠错 / 日期换算
# MrzRealSampleTest   38 个用例 —— 真实护照与通行证样本的位数、取值、字母数字纠错、输入形态容错
# TlvTest              8 个用例 —— BER-TLV 解析、rawStart/rawLength 语义、边界与截断
# ActiveAuthTest      14 个用例 —— 挑战值随机性、RSA/EC 验签、克隆芯片识别、DG15 公钥解析
# CscaTrustStoreTest  11 个用例 —— 信任库解析 / 覆盖范围 / 真实证书上的链式验证
```

关键实现细节（容易踩坑的地方）：

* BAC 密钥派生用的是 **ICAO KDF**：`KDF(K, c) = DESParityAdjust(SHA-1(K ‖ c_be32)[0..15])`，
  而不是早期文档里常见的"3DES 加密 D=1/2"写法；
* ISO 9797-1 Padding Method 2 **在数据已经对齐时仍会追加一整个块**，
  这直接影响 `M.IFD` 的计算；
* 安全报文中命令头必须参与 MAC 计算，且 CLA 固定为 `0x0C`；
* 3DES 模式下 CBC 的 IV 恒为全 0（AES 才需要 `IV = K(SSC)`）。

## 手动输入：填三要素即可

OCR 识别失败时，**不需要输入完整机读区**。芯片访问（BAC）只需要三个要素：

| 字段 | 位数 | 示例 |
|---|---|---|
| 证件号码 | 1~9 位，字母数字混合 | `EF1260892`（护照）、`CA3273201`（通行证） |
| 出生日期 | 6 位 `YYMMDD`（也接受 8 位） | `810803` 或 `19810803` |
| 有效期至 | 6 位 `YYMMDD`（也接受 8 位） | `290117` 或 `20290117` |

**三个校验位由应用自动算出**，无需手工输入。

原理：BAC 口令（MRZi）只需要
`证件号+校验位 ‖ 出生日期+校验位 ‖ 有效期+校验位`，
而每个校验位都可以由字段本身用 7-3-1 加权算法算出，
因此只填三个字段就足以构造出完整的 24 字符口令。

> 这一点有测试保证：`MrzRealSampleTest` 断言
> 「三要素算出的 MRZi」与「从真实护照/通行证 MRZ 解析出的 MRZi」**逐字符相同**。

输入框会自动补足不足 9 位的证件号（右侧补 `<`）、容忍空格与大小写、
并校验日期的月份与日期是否合法。

如果手上有完整 MRZ，也可以切到「粘贴完整 MRZ」模式，整段粘贴会自动拆行。

## 中国通行证的特殊处理

**往来港澳通行证 / 往来台湾通行证**在芯片里的字段布局与标准 TD1 **不同**，
实测两本真实证件的全部校验位都能对上，布局如下（位置从 1 起算）：

```
第 1 行：证件类型码(1-2) 证件号码(3-11) 校验位(12) 填充(13)
         有效期(14-19) 校验位(20) 填充(21)
         出生日期(22-27) 校验位(28) 填充(29) 复合校验位(30)
第 2 行：12 字符附加信息 + 英文姓名（MRZ 格式，如 HUANG<<QUANMIAO）
第 3 行：10 字符附加信息 + 填充
```

注意两点与标准 TD1 的差异：

1. **有效期排在出生日期之前**（标准 TD1 是出生日期在前）
2. 复合校验位覆盖 `证件号+校验位 ‖ 有效期+校验位 ‖ 出生日期+校验位`

**只有当全部校验位（含复合校验位）都通过时才采用此布局**，否则回退标准 TD1 解析，
因此不会误判普通证件。

| 证件类型码 | 证件 |
|---|---|
| `CS`（芯片）/ `S<`（卡面） | 往来港澳通行证 |
| `CD`（芯片）/ `D<`（卡面） | 往来台湾通行证 |

> 二者都以 `C` 开头，**不能只按首字母判断** —— 早期版本因此把往来台湾通行证
> 误标成往来港澳通行证。

### 补充字段来自 DG11

这两类证件的 MRZ 里没有独立性别字段，姓名也只有 MRZ 格式。以下信息取自 DG11：

| DG11 tag | 内容 |
|---|---|
| `0x5F0E` | 中文姓名 |
| `0x5F0F` | **英文姓名**（MRZ 格式，含 `<<` 分隔符） |
| `0x5F10` | **公民身份号码**（18 位） |

性别由公民身份号码第 17 位推断（奇数男、偶数女）。

## MRZ 字段布局

三种格式的**关键字段位数完全一致**（ICAO 9303-3）：

| 字段 | 位数 | 说明 |
|---|---|---|
| **证件号** | **9 位** | **字母数字混合**——护照如 `EF1260892`，往来港澳通行证如 `CA3273201` |
| **出生日期** | **6 位** | `YYMMDD` |
| **有效期** | **6 位** | `YYMMDD` |

区别只在行数与每行字符数：

| 格式 | 行数 × 每行 | 证件号位置 | 出生日期 / 有效期位置 | 适用证件 |
|---|---|---|---|---|
| **TD1** | 3 × 30 | 第 1 行 6-14 | 第 2 行 1-6 / 9-14 | 往来港澳通行证、往来台湾通行证、身份证件卡 |
| **TD2** | 2 × 36 | 第 2 行 1-9 | 第 2 行 14-19 / 22-27 | 旧式身份证件 |
| **TD3** | 2 × 44 | 第 2 行 1-9 | 第 2 行 14-19 / 22-27 | 各国电子护照 |

> **TD1 的第 2 行顺序特殊**：出生日期(6) → 校验位(1) → **性别(1)** → 有效期(6) → 校验位(1) → 国籍(3) → 可选数据(11) → 复合校验位(1)。
> 性别夹在出生日期校验位与有效期之间，这是最容易写错的地方。

BAC 口令（MRZi）由这三段拼成：`证件号+校验位 ‖ 出生日期+校验位 ‖ 有效期+校验位`，恒为 **24 字符**。

**证件号的纠错必须用完整 MRZ 字符集**（`0-9` + `A-Z` + `<`，共 37 个）。
早期版本误把证件号当纯数字处理，纠错字符表只有 `0123456789<`，
一旦校验位不通过就会把 `AB1234567` 规范化成 `481234567`——字母全毁、读卡必然失败。
现已修正，并由 `MrzRealSampleTest` 的 22 个用例锁住（含真实护照与通行证样本）。

**输入形态容错**：以下三种常见情形都能正确解析——

| 情形 | 处理方式 |
|---|---|
| 首尾多出空格 | 先 `trim` 再映射字符（否则空格会被当成填充符 `<`，行长度多 1 位导致检测失败） |
| 整段 MRZ 粘进一个输入框 | 按换行符自动拆行 |
| OCR 把多行识别成一整行 | 总长度为 44 / 30 / 36 的整数倍时按行长自动切开（如护照 88 = 2×44、通行证 90 = 3×30） |

## CSCA 信任库

被动认证只能证明「数据没被改过」。要回答「这张证件是不是某国真签发的」，必须把文档签名证书（DSC）
沿签发关系逐级上溯，直到命中签发国的 CSCA 根证书。本应用内置了这份信任库。

| 项目 | 说明 |
|---|---|
| 证书数量 | 513 张（去重后） |
| 覆盖范围 | 103 个国家/地区 |
| 中国相关 | 33 张 —— 中国护照（外交部）16、中国澳门 8、中国台湾地区 7、中国香港 2 |
| 来源 | 德国 BSI German Master List、荷兰 NPKD Netherlands Master List（均为政府公开发布） |
| 体积 | 826 KB，随 APK 打包，**无需联网** |

> 为什么不用官方 SDK 里的 `db_csca.db3`？因为那份只有 **10 张证书、全部是中国签发**，
> 且其中 2 张已经过期（一张 2024-05-12 失效，一张 2026-02-18 失效）。
> 公开主列表覆盖 103 个国家/地区，且可随时更新，是更好的选择。

**更新信任库**：把新的主列表（ICAO PKD 的 LDIF、或德国/荷兰的 `.ml` 文件）用
`tools/csca/extract_csca.py` 提取证书，再用 `tools/csca/build_bundle.py` 打包，
替换 `app/src/main/assets/csca/csca_bundle.bin` 即可。两个脚本都放在 `tools/csca/` 下。

**信任链判定逻辑**（`nfc/pa/CscaChain.kt`）：从 DSC 出发，用「上一级证书的公钥」验证
「下一级证书的签名」，逐级回溯至自签名根，最大深度 4 层以兼容 CSCA 轮换产生的 link 证书。
找不到签发者、签名不匹配、出现环、超出深度，都会给出明确的失败原因而非静默失败。

## 主动认证（AA）

三道验证解决三个不同的问题，缺一不可：

| 机制 | 回答的问题 | 局限 |
|---|---|---|
| 被动认证（PA） | 数据**有没有被改过** | 无法识破整芯片克隆 |
| CSCA 信任链 | **是不是该国真签发的** | 同上 |
| **主动认证（AA）** | **是不是真芯片**（非克隆） | 需证件启用 AA |

**为什么克隆芯片能骗过前两道？** 攻击者可以把真芯片的全部数据（DG1、DG2、EF.SOD……）原样复制到另一颗可写芯片上。
此时数据组摘要完全一致、DSC 签名完全有效、CSCA 信任链也完全成立——**前两道验证会全部通过**。
唯一的破绽是：克隆芯片里没有真芯片那颗**只存于芯片内部、永不外泄的私钥**。

**AA 如何识破**：

```
读卡器 → 芯片：INTERNAL AUTHENTICATE (INS 0x88)，携带 8 字节随机挑战值
芯片  → 读卡器：用 DG15 中对应公钥的私钥对挑战值签名
读卡器：用 DG15 中的公钥验签 —— 克隆芯片没有私钥，无法生成正确签名
```

挑战值每次随机，因此无法预先录制重放。

**实现要点**：

- 挑战值长度固定 8 字节（`SecureRandom` 生成）
- 命令经**安全报文通道**发送（BAC 之后所有命令都必须如此）
- **签名算法不唯一**：ICAO 9303-11 允许芯片自行选择，只要与 DG15 公钥类型匹配。
  因此实现按 `SHA256withRSA / SHA1withRSA / SHA384withRSA / SHA512withRSA`
  （EC 则为对应的 ECDSA 变体）逐个尝试，命中即通过——这是各家实现的通行做法
- 芯片返回 `6A81`（功能不支持）时判定为**「该证件未启用 AA」而非失败**——
  这是证件的正常配置差异，不应被当作读取错误

## 已知限制

* 只实现 **BAC**。仅支持 PACE 的证件（部分新版电子护照）无法读取，应用会明确报错提示。
  未实现 PACE 的原因：eMRTD 的 PACE 默认使用 **brainpool 曲线**，而 JDK / Android 的 JCE
  不支持该曲线族，也不支持 AES-CMAC，需要自行实现椭圆曲线运算，风险与收益不成比例。
* 已实现**主动认证（AA）**，但未实现**芯片认证（CA）**——CA 只在 PACE 体系下使用，
  依赖同样的 brainpool 曲线支持，因此与 PACE 一并搁置。
  芯片不支持 AA 时（部分证件未启用），应用会如实标注为「未启用」而非判定为失败。
* CSCA 信任库覆盖 103 个国家/地区，但**不含证书吊销列表（CRL）**。
  未实现 CRL 的原因：主列表文件本身不含 CRL，ICAO PKD 的 CRL 需人工接受条款后下载，
  且 CRL 有效期很短、离线打包会迅速失效——连成熟的 gmrtd 库也只解析 CRL 分发点而不做校验。
  信任库来源为德国 BSI 与荷兰 NPKD 公开发布的主列表，可通过替换 `assets/csca/csca_bundle.bin` 更新。
* 信任库中有 199 张证书使用了**显式 EC 参数（自定义曲线）**，JDK / Android 的
  `CertificateFactory` 无法解析，已在打包阶段剔除。若需覆盖这部分证书，需引入 BouncyCastle 等第三方密码学库。
* 人脸图像支持 JPEG；JPEG2000 格式会被识别并原样保存，但 Android 原生无法直接显示。
* 无网络、无云端，所有数据仅存本机。

## 权限清单

应用只申请以下权限：

| 权限 | 用途 | 类型 |
|---|---|---|
| `android.permission.CAMERA` | 拍摄证件资料页，OCR 识别 MRZ | 危险权限，运行时申请 |
| `android.permission.NFC` | 读取电子证件芯片 | 普通权限 |
| `android.permission.ACCESS_NETWORK_STATE` | 无实际用途，来自 ML Kit 的传递依赖 | 普通权限，**只读**，不能传输数据 |

### 关于 INTERNET 权限

**应用显式移除了 `android.permission.INTERNET`。**

ML Kit 的传递依赖 `com.google.android.datatransport:transport-backend-cct`
（Google 的遥测上报组件）会在清单合并时声明 `INTERNET` 与 `ACCESS_NETWORK_STATE`。
本应用完全离线，不需要任何网络能力，因此在 `AndroidManifest.xml` 中用
`tools:node="remove"` 将其移除：

```xml
<uses-permission android:name="android.permission.INTERNET" tools:node="remove" />
```

**移除后的效果**：应用在**系统层面**无法发起任何网络连接。即使某个库尝试上报数据，
系统也会直接以 `SecurityException` 拒绝——这比「代码里不写网络调用」更可靠，
因为它不依赖于对每一个依赖库的信任。

可以用 `aapt2 dump badging` 自行验证：

```bash
aapt2 dump badging apk/EdocReader-1.0.5-release.apk | grep uses-permission
# 输出中不会出现 android.permission.INTERNET
```

> 说明：`ACCESS_NETWORK_STATE` 予以保留。它是只读的连通性查询权限，不允许传输任何数据；
> 移除它可能让遥测调度器在查询网络状态时抛异常。若追求极致，也可以一并移除，
> 但需要在真机上验证 ML Kit 不因此崩溃。

## 合规与隐私

读取证件芯片涉及**敏感个人信息与生物特征信息**。

* 请仅对**本人证件**或**已取得持证人明确书面授权**的证件使用本应用；
* 遵守《中华人民共和国个人信息保护法》《中华人民共和国出境入境管理法》等法律法规；
* 应用**未申请 INTERNET 权限**，在系统层面无法联网、无法上传任何数据，
  读取结果保存在应用私有目录，卸载即清除，
  且已显式排除在系统备份/迁移之外（见 `res/xml/backup_rules.xml`）；
* 导出的文件包含完整证件信息与人脸图像，请自行妥善保管、按需删除；
* 本项目为技术演示，不构成任何形式的合规意见。
