第 1 章　研究背景与结论摘要

1.1　报告要解决的问题

出入境证件（电子护照、往来港澳通行证、往来台湾通行证等）内含符合 ISO/IEC 14443 的非接触式芯片， 芯片中保存着经签发国数字签名的持证人资料与人脸图像。读取这些数据需要一套完整的软硬件链路： 摄像头识别机读区、NFC 建立通信、密码学认证、按标准解析数据结构、验证签名。

官方提供的《出入境证件电子信息识读认证软件》SDK 封装了上述全部能力，但存在两个现实约束： 其一，SDK 依赖授权文件、设备指纹与服务端校验，无授权文件无法工作； 其二，授权与设备绑定，难以在自有设备上自由部署。 本报告要回答的核心问题是：这套读证能力，究竟是必须依赖官方 SDK 的私有技术，还是可以通过公开国际标准独立实现？

1.2　核心结论

结论一：读证能力完全由公开国际标准定义。 证件芯片的数据结构、访问控制协议、安全报文格式、签名验证方式，全部由 ICAO Doc 9303 明确规定， 是公开的、可独立实现的国际标准，不属于任何厂商的私有技术。
结论二：官方 SDK 的壁垒不在算法，而在工程积累与授权体系。 SDK 真正的独占资产是：中国证件专用 OCR 训练集、中国 CSCA 证书库、以及服务端的查验结论能力。 算法层面（BAC、安全报文、数据组解析）无任何独占性。 而且经实测，其 CSCA 库仅 10 张证书、全部是中国签发、其中 2 张已过期—— 公开主列表可提供 513 张、覆盖 103 个国家/地区的更新数据，这一项壁垒也远没有想象中高。
结论三：独立实现是可行且已经验证的。 本项目从零实现的 BAC 认证与安全报文，已用 ICAO Doc 9303 Part 11 附录 D 的官方工作样例 逐字节比对通过；全部 61 项单元测试通过；已构建出可安装的 Android 应用， 并内置 CSCA 信任库完成签发国信任链验证、实现主动认证完成芯片克隆检测。
结论四：绕过官方 SDK 的授权校验不可行、不必要、且存在法律风险。 授权校验包含服务端环节，本地无法绕过；且绕过技术保护措施可能违反《著作权法》与《刑法》相关规定。 由于标准是公开的，正确路径是独立实现，而非破解。

第 2 章　官方 SDK 逆向分析

2.1　产品形态与总体定位

该软件以 SDK 形式交付，面向需要在自有系统中集成出入境证件识读能力的集成商， 提供 Android 与 Windows 两个平台的实现。其功能覆盖两大环节： 光学识读（识别证件表面机读区 MRZ 与视读区信息）与 芯片识读（通过 NFC / PC-SC 读取芯片内加密数据）。

两个平台的实现共享同一套底层能力模型：OCR 引擎 + 芯片通信 + 密码学 + 数据解析 + 授权校验。 差异主要在外围：Android 侧走手机 NFC 与摄像头，Windows 侧走 PC/SC 读卡器与摄像头。

第 3 章　证件识读的技术原理

3.1　eMRTD 体系与 ICAO Doc 9303

国际民航组织（ICAO）制定的 Doc 9303《机读旅行证件》 是全球电子证件的技术基准。 中国作为 ICAO 缔约国，所签发的电子护照、电子往来港澳通行证、电子往来台湾通行证 均遵循该标准。标准分为三个关键部分：

图 3-1　ICAO Doc 9303 的三个关键部分及其数据流向

3.2　机读区 MRZ 规格

MRZ 是证件表面按固定格式印刷的等宽字符区域，其作用有二： 一是供机器快速读取基本信息；二是作为芯片访问控制口令的来源。 MRZ 有 3 种规格，区别在行数与每行字符数：

规格尺寸适用证件说明
TD13 行 × 30 字符身份证件卡、往来港澳/台湾通行证卡式证件，MRZ 印在背面
TD22 行 × 36 字符部分国家的身份证、签证较少见
TD32 行 × 44 字符各国电子护照（含中国普通护照）最常见的规格

以 TD3（护照）为例，两行的字段划分如下：

图 3-2　TD3 机读区的字段布局（数字为字段序号，灰底为校验位）

需要特别指出：三种格式的关键字段位数完全一致，区别只在行数与每行字符数。 这一点在实际开发中很容易记错，也是本项目早期一个缺陷的根源。

字段位数说明
证件号9 位字母数字混合——护照如 EF1260892，往来港澳通行证如 CA3273201
出生日期6 位YYMMDD
有效期6 位YYMMDD
格式行数 × 每行证件号位置出生日期 / 有效期位置适用证件
TD13 × 30第 1 行 6-14第 2 行 1-6 / 9-14往来港澳通行证、往来台湾通行证、身份证件卡
TD22 × 36第 2 行 1-9第 2 行 14-19 / 22-27旧式身份证件
TD32 × 44第 2 行 1-9第 2 行 14-19 / 22-27各国电子护照
TD1 第 2 行的字段顺序特殊，是最容易写错的地方：
出生日期(6) → 校验位(1) → 性别(1) → 有效期(6) → 校验位(1) → 国籍(3) → 可选数据(11) → 复合校验位(1)。
性别字段夹在出生日期校验位与有效期之间，而 TD2/TD3 的性别在出生日期校验位之后、有效期之前， 位置不同。按 TD3 的习惯去读 TD1 会导致有效期与国籍整体错位一位。
另一个易错点：证件号不是纯数字。 中国护照号（EF1260892）与往来港澳通行证号（CA3273201）都含字母。 对证件号做「字母→数字」规范化会把它破坏成 8F1260892 之类， 进而导致 BAC 口令错误、读卡失败。证件号的纠错必须在完整 MRZ 字符集 （0-9 + A-Z + <，共 37 个）内进行。

3.3　校验位算法

MRZ 中每个数字字段后都跟一位校验位，算法在 ICAO Doc 9303 Part 3 中定义： 对字段中每个字符取「字符值」，乘以循环权重 7、3、1，求和后对 10 取模。 字符值映射规则为：0-9 → 0-9，A-Z → 10-35，< → 0。

第 4 章　协议握手过程详解

4.1　BAC 握手完整时序

BAC（Basic Access Control）是整个读证流程的核心。它的设计思想是： 把证件表面可见的 MRZ 文本当作「口令」，只有能读到证件实体的人才能打开芯片。 握手过程共 10 步，其中第 4、7、12 步是本地计算，不产生通信：

图 4-1　BAC 握手与安全报文建立完整时序（灰底为本地计算，无网络交互）
为什么 BAC 能防止随意读取？ 芯片不接受任何未认证的读请求。而 BAC 口令由 MRZ 中的证件号、出生日期、有效期三段拼接而成 （含各自校验位，共 24 字符），必须物理接触证件才能获得。 这意味着「拿一个 NFC 读卡器贴近路人的包」无法读取任何数据—— 这既是隐私保护，也是本方案合法性的基础：读取自己或已获授权的证件，是标准赋予的能力。

4.2　密钥派生 KDF

BAC 的密钥派生有一个广为流传的错误写法：早期很多资料称「用 3DES 加密常量 1 和 2 得到 Kenc 和 Kmac」。 ICAO Doc 9303 Part 11 的正式定义其实是基于 SHA-1 的 KDF：

图 4-2　从 MRZ 文本到会话密钥的完整派生链路

4.3　安全报文封装与解封

BAC 成功后，所有命令与响应都必须套上安全报文（Secure Messaging）外壳。 其本质是：把原始 APDU 的命令头与数据装进若干数据对象（DO），加密后附加 MAC。

图 4-3　安全报文的封装结构与解封校验流程
三个最容易踩坑的实现细节：
① ISO 9797-1 Padding Method 2 在数据已对齐时仍会追加一整个块（如 32 字节补到 40 字节）， 这直接影响 M.IFD 的计算结果；
② 命令头必须参与 MAC 计算，且计算前 CLA 要置为 0x0C、并做 Padding；
③ 3DES 模式下 CBC 的初始向量恒为全 0（只有 AES 才需要 IV = K(SSC)）。

4.4　会话计数器 SSC

SSC 是 8 字节大端计数器，每收发一条命令自增 1，并参与 MAC 计算。 它的作用是防止重放攻击：即使攻击者截获了一条合法报文，重放时 SSC 已变，MAC 校验必然失败。

图 4-4　SSC 的构造方式与推演过程

4.6　被动认证流程

第 5 章　本项目的技术方案

5.1　总体架构与设计原则

本项目（EdocReader）以「完全离线、无需任何授权文件」为前提，从零实现了一套完整的证件识读能力。 设计遵循四条原则：

  • 标准优先——严格按 ICAO Doc 9303 实现，不引入任何非标准约定，保证与其他合规实现互通；
  • 零授权依赖——不使用任何需要许可文件、设备绑定或联网校验的组件；
  • 零第三方密码学库——密码学全部使用 JDK / Android 自带的 JCE，减少供应链风险与体积；
  • 可验证——所有密码学环节都用 ICAO 官方工作样例做逐字节断言，而非「看起来能跑」。

5.3　OCR 识别方案

OCR 环节的目标不是「识别所有文字」，而是「稳定提取 MRZ 行组并让校验位全部通过」。 因此方案围绕校验位展开：把校验位当作识别质量的判据。

图 5-2　以校验位为判据的 MRZ 识别与纠错流程

5.3.1　OCR 失败时的兜底：只需三个字段

OCR 不可能 100% 成功（反光、折角、磨损都会导致识别失败）。 但芯片访问本身只需要三个要素——证件号、出生日期、有效期， 因为 BAC 口令（MRZi）就是 证件号+校验位 ‖ 出生日期+校验位 ‖ 有效期+校验位， 而三个校验位都可以由字段本身用 7-3-1 加权算法算出。

因此手动输入界面的默认模式是「填三要素」而非「粘贴完整 MRZ」： 用户只需输入三个字段，应用自动补足 9 位证件号、计算三个校验位、 拼出完整的 24 字符口令。

这一等价关系有测试保证： fromThreeElements("EF1260892", "850320", "290117") 得到的 MRZi， 与从真实护照两行 MRZ 解析得到的 MRZi 逐字符相同 （EF1260892185032082901178）。通行证同样通过。

设计教训（值得记录）：早期版本把手动输入做成了「必须粘贴完整机读区」， 是按内部数据结构的形状去设计输入——因为解析器吃的是 MRZ 文本。 但用户面对的任务是「读芯片」，需要的输入只有三个字段。 输入界面应当从用户的任务出发设计，而不是从内部数据结构的形状出发。

为什么这个方案有效？ MRZ 的校验位设计使得「单字符误识」几乎必然导致校验失败，而「全部校验位通过」 意味着整体识别正确的概率极高。用校验位做判据，比用「识别置信度」可靠得多—— 置信度高的错误识别依然会让校验位失败，而校验位通过的结果几乎不可能是错的。

5.6　CSCA 信任库与信任链验证

被动认证只能证明「数据没被改过」。要回答「这张证件是不是某国真签发的」， 必须把文档签名证书（DSC）沿签发关系逐级上溯，直到命中签发国的 CSCA 根证书。 本节说明这份信任库的来源、规模与验证逻辑。

5.6.1　为什么不直接用官方 SDK 的证书库

官方 SDK 的 Android 包中带有 assets/db_csca.db3（SQLite 格式）。 实测其 tb_csca 表只有 10 条记录，且全部是中国签发， 其中 2 张已经过期：

证书主体序列号有效期至状态
台湾居民来往大陆通行证 CSCA6afc9716…2024-05-12已过期
China Passport CSCA706e2cbc…2026-02-18已过期

只有 10 张、全部是中国、部分已过期——这远不足以支撑可信的信任链判定。 公开渠道能获得更新、更全的主列表，因此本项目改从公开来源获取。

.ml 文件是 CMS SignedData 格式（外层 OID 1.2.840.113549.1.7.2）， 用 openssl cms -verify -inform DER -noverify 可解出内层内容， 其结构为 SEQUENCE { INTEGER version, SET OF SEQUENCE(certificate) }。 遍历该 SET 即可取出全部证书。

所有使用显式 EC 参数（自定义曲线）的证书，报 Only named ECParameters supported。 而 cryptography 能容忍映射到标准曲线（secp256r1 等）的显式参数，因此两者判断相差 65 张。 结论：必须用 JDK 自身的解析器做预筛选，不能依赖第三方库的判断。

5.7　主动认证（AA）与芯片克隆检测

前三道验证（数据摘要、CMS 签名、CSCA 信任链）解决的都是「数据与签发者」的可信问题， 它们有一个共同的盲区：无法区分真芯片与克隆芯片。

攻击者可以把真芯片的全部数据（DG1、DG2、EF.SOD……）原样读出并写入另一颗可写芯片。 此时数据组摘要完全一致、DSC 签名完全有效、CSCA 信任链也完全成立—— 前三道验证会全部通过。唯一的破绽是：克隆芯片里没有真芯片那颗 只存于芯片内部、永不外泄的私钥。

第 7 章　合规、隐私与结论

7.1　法律与合规边界

关于「绕过官方 SDK 授权校验」的明确结论：不可行，也不应尝试。

法律层面：SDK 的授权校验（本地授权文件 + 设备指纹 + 服务端签发）属于技术保护措施。 规避该类措施可能违反《著作权法》第五十三条、《计算机软件保护条例》的相关规定； 而服务端校验环节位于国家移民管理局体系的信息系统，绕过或伪造请求可能触及 《刑法》第二百八十五条（非法获取计算机信息系统数据、非法控制计算机信息系统） 与第二百八十六条（破坏计算机信息系统）。

技术层面：核心逻辑位于原生机器码且带完整性自校验，设备指纹由系统 API 实时采集， 最终的授权数据由服务端签发——本地改造无法获得服务端认可，这是根本性阻断点。

必要性层面：读证流程完全由公开国际标准定义，不存在必须依赖官方 SDK 的技术环节。 既然标准是公开的，正确路径就是独立实现，而非破解。

合法使用的边界：

  • 仅对本人证件，或已取得持证人明确书面授权的证件使用本应用；
  • 遵守《中华人民共和国个人信息保护法》《中华人民共和国出境入境管理法》等法律法规；
  • 不得用于伪造、变造证件，不得用于冒用他人身份，不得用于任何形式的身份欺诈；
  • 作为用人单位、金融机构等处理他人证件信息时，须具备法定事由并履行告知同意义务。

7.2　隐私保护设计

证件芯片数据包含敏感个人信息与生物特征信息（人脸图像），本项目在工程上做了以下约束：

设计点实现方式
不联网显式移除 INTERNET 权限，数据无任何出境路径。 ML Kit 的传递依赖 com.google.android.datatransport:transport-backend-cct （Google 遥测上报组件）会在清单合并时声明 INTERNET 与 ACCESS_NETWORK_STATE， 本项目用 tools:node="remove" 将其移除，使应用在系统层面无法发起任何网络连接—— 即使某个库尝试上报，也会被系统以 SecurityException 拒绝
不写外部存储数据保存在应用私有目录，其他应用无法访问
卸载即清除私有目录随应用卸载一并删除
排除系统备份通过 backup_rules.xml 与 data_extraction_rules.xml 显式排除记录目录与配置，避免证件数据进入云备份或换机迁移
导出需用户确认通过系统文件选择器由用户指定位置，应用不静默落盘
最小权限仅申请相机与 NFC 两项功能必需权限； 另有一个来自 ML Kit 的 ACCESS_NETWORK_STATE（只读的连通性查询权限，不能传输数据）

7.3　能力边界与后续演进

当前能力边界（如实说明）：

  • 仅实现 BAC。若证件为 PACE-only，则无法读取，应用会明确报错而非静默失败；
  • 已实现主动认证（AA），可排除芯片克隆；但未实现芯片认证（CA）——CA 只在 PACE 体系下使用， 依赖同样的 brainpool 曲线支持，因此与 PACE 一并搁置；
  • 未实现 PACE 的原因：eMRTD 的 PACE 默认使用 brainpool 曲线，而 JDK / Android 的 JCE 不支持该曲线族，也不支持 AES-CMAC，需自行实现椭圆曲线运算，风险与收益不成比例；
  • 信任库不含证书吊销列表（CRL），无法反映已吊销的证书；
  • 信任库中有 199 张证书使用了显式 EC 参数（自定义曲线），JDK / Android 无法解析，已在打包阶段剔除；
  • 人脸图像支持 JPEG；JPEG 2000 格式可被识别并原样保存，但 Android 原生无法直接显示；
  • 往来港澳通行证、往来台湾通行证在格式与协议层面已支持（TD1 三行机读区 + BAC）， 但尚未经过真机验证，实际可用性取决于证件是否支持 BAC 以及 OCR 识别率。

后续演进方向（按性价比排序）：

优先级方向预期收益

高PACE 支持覆盖仅支持 PACE 的新版证件，显著扩大可用范围

7.4　总结

本报告的核心判断可以归纳为一句话：

出入境证件识读能力完全由公开国际标准（ICAO Doc 9303）定义， 官方 SDK 的价值在于中国证件专用 OCR 模型、CSCA 证书库与服务端查验结论这类工程积累， 而不在于算法本身的独占性。因此，独立实现是一条可行、合法且已经验证的路径。

本项目用「零授权依赖、零第三方密码学库、完全离线」的方式完成了这条路径： BAC 与安全报文已通过 ICAO 官方向量逐字节验证，92 项单元测试全部通过， 并内置了覆盖 103 个国家/地区的 CSCA 信任库，完成从数据完整性到签发国可信的完整验证链路； 同时实现主动认证，具备芯片克隆检测能力。源码与 APK 均已交付。

同时必须正视能力边界：缺少 PACE 支持、缺少证书吊销列表， 意味着当前实现尚不能替代官方 SDK 在强监管场景下的地位。 但在个人自查、自有设备集成、技术研究与教学等场景中， 它提供了一条不受授权约束、数据不出设备、代码完全可控的技术选择。

B.3　往来港澳通行证的身份号码为密文（未解）

实测同一持有人在两本证件上 0x5F10 的取值：

证件该字段内容
往来台湾通行证110101199001011234　明文，正常
往来港澳通行证HKLMDEGCEBFOMGKGIIMGKAHHIPOFLMBO　32 个字母

分析过程：

  • 字母只用到 A–P 十六个，即每个字母携带 4 位 → 共 16 字节
  • 同一证件读取两次，结果完全相同 → 不是会话密钥加密，而是芯片侧的固定变换
  • 对身份号码原文、BCD 形式、证件号、MRZ 第 1 行等分别试过 MD5 / SHA-1 / SHA-256，均不匹配

结论：这 16 字节很可能是芯片内以固定密钥加密的身份号码，没有密钥无法还原。 EdocReader 的处理方式是：只采用真正的 18 位身份号码，否则如实标注 「芯片中为加密形式，本应用无法解读」，不把密文当作身份号码展示。

B.4　DG2 面部图像为 JPEG 2000，Android 需自带解码器

实测中国签发的往来港澳/台湾通行证，DG2 中的面部图像是 JPEG 2000 裸码流（以 FF4F FF51 即 SOC + SIZ 开头）， 而非 JPEG。实测参数： 

尺寸      354 × 472
分量数    3（8 位无符号）
小波      5 级 5/3 可逆（整数）
层数      1
进度      LRCP
码块      64 × 64
颜色变换  MCT = 1（启用）

Android 平台不内置 JPEG 2000 解码器，BitmapFactory 与 ImageDecoder 对它均返回 null。EdocReader 的解决方式是内嵌纯 Java 的 jj2000 解码核心（166 个文件，约 4.6 万行，许可证允许用于符合 JPEG 2000 标准的实现）， 并自写适配层把输入改为内存数组、直接取回像素数组。

验证方式：以 Pillow（OpenJPEG）的解码结果为基准逐像素比对 —— 6745 个采样点平均差 0.000、最大差 0，完全一致。

B.5　官方 SDK 的 Lua 脚本（.nlc）逆向进展

bin/pscp.lar 实为 ZIP，内含编译过的 Lua 脚本： mrz.nlc / dg11.nlc / dg13.nlc / funcs.nlc / start.nlc。

已确认是 Lua 5.3 字节码：

  • 魔数 1B 4C 75 61 53 = Lua + 版本 0x53
  • 常量表标签 04（短字符串）与 13（整数）与 Lua 5.3 定义完全吻合 （LUA_TSHRSTR = 4、LUA_TNUMINT = 0x13）

厂商改动（这是反编译失败的原因）：

位置标准值本 SDK
byte 5 format003F
byte 6–11 LUAC_DATA19 93 0D 0A 1A 0A4E 4C 0D 0A 43 0A（NL C ）
byte 17–24 LUAC_INT0x56780x8457

把上述四处补成标准值后，反编译器能通过头部校验，但随后 lastlinedefined 读成 16777216 并导致内存溢出 —— 说明 proto 头部的字段宽度或顺序也被改动，必须修改反编译器源码才能继续。

替代路线：与其继续反编译，不如直接导出芯片原始数据组字节 （EdocReader v1.0.12 起随导出包提供 rawDg1Hex / rawDg11Hex / rawDg2HeadHex），即可在本地精确复现，无需反编译。
